# Розробка

Go 1.26+. Одна пряма залежність — [go-sqlite3](https://github.com/ncruces/go-sqlite3):
SQLite, перекладений у чистий Go (wasm2go), без cgo і без JIT. Тому бінарник
статичний, однаковий для будь-якого Linux і працює з `MemoryDenyWriteExecute=yes`.

## Збірка

```bash
go build -o alertd .                                     # для себе
scripts/package.sh 1.0.0                                 # реліз: dist/alertd-1.0.0.tar.gz + SHA256SUMS
```

## Тести

```bash
go test ./...                                                     # модульні
go build -o /tmp/alertd . && ALERTD_BIN=/tmp/alertd go test ./...  # + наскрізні (справжній бінарник)
go build -race -o /tmp/alertd-race . && \
  ALERTD_BIN=/tmp/alertd-race BURST=500 go test -race ./...       # гонки
SOAK=1 ALERTD_BIN=/tmp/alertd go test -run TestSoak -v .          # навантаження: 20 000 webhook
CHROME=1 go test -run TestLiveIndicatorInChrome -v .              # справжній headless Chrome
go test -run '^$' -fuzz FuzzWebhookBody -fuzztime 60s .           # фазинг
go test -run '^$' -bench . .                                      # бенчмарки
```

| Група | Що перевіряє |
|---|---|
| Модель | 60 випадкових сценаріїв: події кожного регіону перемішані, з дублікатами й паралельно (8 потоків); підсумковий стан = останній за часом знімок; БД узгоджена (активні = відкриті сесії); 2 000 упорядкованих кроків — кожен тип зміни збігається з моделлю |
| Рівні загроз | усі 256 послідовностей переходів між «спокій», жовтий (БпЛА) і червоний (ракети): тип зміни, `levels`/`prevLevels`, сесії рівнів у БД |
| Стан | переходи з документації ukrainealarm, звірка, ретенція, дозаповнення областей; сценарії з реальних даних: повтори в `/alerts`, webhook пізніший за звірку, запізнілий webhook після відбою, webhook новіший за знімок |
| Атаки | шляхи й методи → 404, підписи → 401, повтори, завеликі тіла, ворожі клієнти |
| Збої | сміттєві відповіді API, масовий відбій, відмова диска |
| Наскрізні | старт, звірка пропущеного, перезапуск посеред тривоги, потік подій із відновленням (`hello`, `epoch`, `resync`), сторінки, `check` без витрати ліміту, ліміт API без жодного 429 |
| Навантаження | 3 000 і 20 000 webhook, пам'ять, порядок у 16 підписників |
| Фазинг | випадкові тіла webhook: без панік, некоректне не проходить |

Якість тестів перевірено мутаціями: навмисні поломки ключової логіки (перевірка часу,
секрету, дублікатів, розміру, порядку подій, пріоритету webhook, приховування на
головній тощо) ловить хоча б один тест.

## Швидкодія (2 ядра)

| Що | Результат |
|---|---|
| Повна обробка підписаного webhook | ~55 мкс, з них ~40 — перевірка RSA |
| Оновлення стану в пам'яті | ~7 мкс |
| 20 000 webhook, 128 паралельно, 16 підписників | ~6 000 запитів/с; кожен підписник отримав усі події по порядку; пам'ять ≤ 140 МБ |
| Старт / перезапуск | ~0,01 с |

Реальна затримка ukrainealarm → сервер (423 webhook): медіана 4,2 с, p90 12 с,
p99 25 с, максимум 56 с. Обробка в alertd додає менше 1 мс.

## Реліз

1. Оновити `CHANGELOG.md` (розділ `## X.Y.Z`).
2. `git tag vX.Y.Z && git push --tags` — або вручну: **Actions → release → Run workflow**, версія `X.Y.Z` (тег створить GitHub).
3. GitHub Actions проганяє тести й `govulncheck`, збирає бінарники найсвіжішим Go,
   додає атестацію походження й публікує реліз з архівом і `SHA256SUMS`.

## Структура

| Файл | Що |
|---|---|
| `main.go` | налаштування, команди, запуск, звірка з API |
| `server.go` | публічний обробник (webhook, сторінки) і локальний API |
| `verify.go` | перевірка RSA-підпису, ключ |
| `state.go` | стан у пам'яті, узгодження webhook і знімків, потік подій |
| `model.go` | формати ukrainealarm, рівні загроз |
| `store.go` | SQLite: схема, пакетний запис, ретенція |
| `upstream.go` | клієнт API ukrainealarm з урахуванням ліміту |
| `pages.go`, `www/` | публічні сторінки та індикатор |
| `deploy/` | unit systemd, `alertd-install.sh` (встановлення з архіву), `alertd-update.sh` (оновлення з GitHub Releases), шаблон налаштувань, ключ підпису ukrainealarm |
