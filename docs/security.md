# Безпека

## Модель загроз

alertd стоїть в інтернеті й приймає запити від будь-кого. Нападник може: сканувати
сайт, підбирати секрет, надсилати підроблені чи повторені webhook, засипати сервер
запитами, тримати повільні з'єднання, підсовувати сміття. Також може збоїти сам
API ukrainealarm (порожня відповідь, обрізаний JSON) або диск сервера.

Мета: ніхто, крім ukrainealarm, не може змінити стан; зовні не видно, що це за сервіс;
збої джерела не перетворюються на хибний «відбій»; сервіс працює далі за будь-якого
навантаження чи помилки.

## Захист на кожному рівні

| Рівень | Захист |
|---|---|
| Мережа | назовні лише reverse proxy з TLS; alertd слухає loopback; локальний API (`LOCAL_LISTEN`) примусово лише loopback — інакше сервіс не стартує |
| CDN (необов'язково) | приховує IP сервера; на сервері 443 відкритий лише для мереж CDN ([proxy.md](proxy.md)) |
| Публічні адреси | лише `GET /`, `GET /s` і `POST /hook/<секрет>`; решта — однакова 404, тож не видно, чи вгадано секрет або метод |
| Розмір | тіло ≤ 256 КБ: за `Content-Length` відмова до читання, без нього — обрізання; заголовки ≤ 32 КБ |
| Повільні клієнти | тайм-аути: заголовки 5 с, читання 15 с, запис 15 с, простій 120 с |
| Секрет у шляху | 24–128 символів `[A-Za-z0-9_-]` (типово 48 hex), порівняння за сталий час. Може засвітитись у журналах proxy/CDN — тому це лише додатковий шар |
| Підпис | RSA PKCS#1 v1.5 + SHA-256 над `{timestamp}.{тіло}`; ключ ≥ 2048 біт, закріплений файлом; у журналі відбиток ключа, будь-яка його зміна записується; новий ключ береться лише з API ukrainealarm через HTTPS і не частіше ніж раз на 5 хв |
| Повтори | позначка часу ±5 хв; повторне тіло відкидається (15 хв у пам'яті + `UNIQUE` у БД; після перезапуску пам'ять відновлюється з БД). Дедуплікація — лише після перевірки підпису, тож чужі запити не засмічують пам'ять |
| Поля | `regionId` — лише цифри ≤ 16, обмеження довжини типів, рівнів і причин, ≤ 64 рівні; некоректне — в журнал і `ignored` |
| Відповіді API | лише `https` (http — тільки loopback для тестів); перенаправлення не виконуються; тіло має бути JSON-масивом — порожня відповідь, `null` чи сміття ≠ «тривог немає»; масовий відбій (> половини активних) — лише після підтвердження наступним знімком |
| Майбутній час | позначки часу з «майбутнього» обрізаються, тож не можуть заблокувати стан регіону |
| Сторінки | CSP `default-src 'none'`, заборона фреймів, `nosniff`, `no-referrer`, `noindex`, `no-store`; сторінки помилок без скриптів; на головній рівно один скрипт за хешем; ні назв, ні чисел, ні часу; `SITE_TITLE` екранується |
| Аварії | паніка в обробнику → сторінка 500 і запис у журнал; збій диска не зупиняє прийом webhook |
| Журнал | керівні символи екрануються; відхилені запити — не більше 10 записів на хвилину плюс зведення |
| Процес | користувач `alertd`, без привілеїв і capabilities, `ProtectSystem=strict`, приватні `/tmp` і пристрої, фільтр системних викликів, лише IPv4/IPv6/Unix-сокети, `MemoryDenyWriteExecute` (впроваджений код не запуститься), пам'ять ≤ 256 МБ; `systemd-analyze security` — **1.3 OK** |
| SQLite | у чистому Go, без cgo і JIT; `trusted_schema=OFF`; пам'ять ≤ 64 МБ |
| Файли | `alertd.env` — `600 root` (сервіс отримує змінні від systemd, сам файл прочитати не може); БД — `/var/lib/alertd` (`750 alertd`) |
| Ланцюжок постачання | одна пряма залежність (go-sqlite3); `go.sum` перевіряється; CI запускає `govulncheck`; дії GitHub закріплені за комітами; релізи — з атестацією походження (`gh attestation verify`) |

Публічних точок, які щось змінюють, немає: webhook лише додає події, усе інше —
тільки локально.

## Перевірено тестами

- 23 варіанти шляхів і методів (регістр, `..`, `%00`, `//`, обрізаний секрет) → 404;
- 11 варіантів підпису (без підпису, чужий ключ, зміщений час, інше тіло, інший алгоритм) → 401;
- повтор → `dup`, завеликі тіла → 413 до читання;
- ворожі клієнти: повільні, обірвані, тисячі з'єднань;
- сміттєві відповіді API, масовий відбій, відмова диска;
- фазинг тіла webhook (сотні тисяч випадкових тіл);
- справжній браузер: скрипт працює лише за правильного хешу в CSP;
- наскрізні тести під `prctl(PR_SET_MDWE)` — тим самим механізмом ядра, що й `MemoryDenyWriteExecute`;
- мутаційне тестування: 25 навмисних поломок ключової логіки — кожну ловить хоча б один тест.
